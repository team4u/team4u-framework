## Decision

Team4u 1.0 is a breaking convergence release. It publishes one coherent dependency graph, removes misleading compatibility bridges, and splits only boundaries that represent a real runtime choice for consumers. There is no parallel 0.x compatibility layer and no deprecated bridge artifact.

The root POM is simultaneously the parent, aggregator, and complete BOM. No separate `team4u-framework-bom` artifact is created. Pure grouping POMs are removed, and consumers depend on concrete artifacts managed by the root BOM.

## Principles

1. Keep Java 8 as the production bytecode target.
2. Preserve a runnable first-use path for every functional area.
3. Prefer explicit adapter artifacts over optional production dependencies that leak into core.
4. Do not split a module unless the split separates a provider, runtime, or integration decision.
5. Keep each migration independently testable and revertable.
6. Use consumer classpaths, dependency bans, and dependency trees rather than JAR count or size thresholds.
7. Implement and review every task through fresh implementation and review subagents.

## Approved Module Decisions

### Maven Foundation

The root `team4u-framework` POM becomes the only parent, aggregator, and BOM. It manages all released Team4u artifacts and plugin versions. The grouping artifacts `team4u-serializer`, `team4u-config`, `team4u-kv`, `team4u-lease`, and `team4u-retry` are removed. The Aliyun repository is deleted.

CI runs JDK 8, 11, 17, and 21. External Maven Invoker consumers prove minimal, provider, and adapter classpaths.

### Base And Criterion

`team4u-base-jdbc` is extracted. Base keeps utility, cache, refresh, and pattern primitives without Spring, Criterion, Jackson, ByteBuddy, or JDBC. `SpringUtil` is deleted; callers use the existing bean manager boundary.

Base owns a new pure-Java `PathPatternMatcher`. It has no Spring or Criterion dependency and does not encode Criterion DSL semantics. Criterion keeps only its DSL adapter and becomes free of Spring production code after migration.

The matcher preserves the Ant-style semantics already used by Criterion, including `/` as separator, segment-local `*`, directory-crossing `**`, literal backslash, and existing null behavior. A characterization suite locks those semantics before the implementation changes.

### Proxy And Serializer

Proxy remains one artifact. ByteBuddy becomes optional: JDK interface proxies work without it, and class proxies fail with an actionable message naming the optional dependency.

Serializer remains exactly two artifacts: `team4u-serializer-json` API and `team4u-serializer-jackson` provider. Core modules depend only on the API; the Jackson provider is supplied by consumers or explicit adapter modules.

### Configuration

`team4u-config-core` supports scalar reads, snapshots, and explicit binding without a proxy implementation, Spring, or a Jackson runtime provider. Proxy construction is inverted behind `ConfigProxyCreator`. If no provider is configured or discoverable, `ConfigManager.createProxy(...)` fails fast with a message that explicitly recommends `com.team4u:team4u-config-proxy`; it never silently returns a bound POJO instead of a Live proxy.

The proxy implementation moves to `team4u-config-proxy`, discovered through `ServiceLoader`. Spring support moves to `team4u-config-spring`, exposed as a plain Spring 5.3 `@Configuration` imported explicitly with `@Import`. There is no Spring Boot dependency, no auto-configuration naming, and no `META-INF/spring.factories`.

Global configuration initialization becomes lazy and resettable. Registration through `ConfigBootstrap.global()` refreshes an initialized global manager automatically.

### Retry

`team4u-retry-core` keeps DTOs, parser, policies, backoff, concurrency APIs, and inline execution. `Retries` supports only `INLINE`; `Retries.managed` is removed.

Managed governance moves to `team4u-retry-managed`, whose explicit facade is `ManagedRetries.with(ManagedRetryClient)`. `ManagedSubmitResult` moves to the managed package to avoid a split core API package. Config-driven policy refresh moves to `team4u-retry-config`. Proxy, lease-runtime, and Spring adapters depend downward on core and managed modules without cycles.

### KV

The functional baseline is `a4f9d9d`, including decorator cascade close and capability passthrough. KV heartbeat is already fixed at that baseline and is outside this project.

Typed JSON spaces move to `team4u-kv-space`. KV core keeps store, memory, tiered, observed, lock/cleaner/polling capability, and hot-swap behavior without proxy or serializer production dependencies. `HotSwapStore` uses a KV-local hot-swap contract and JDK dynamic proxy, preserving baseline close and capability semantics. No KV heartbeat task is added.

### Router And Translator

Router splits only into `team4u-router` and `team4u-router-proxy`. Core owns route definitions, policy parsing, matching, trace, and interceptors. Proxy owns `@Routed`, proxy interception, and bean resolution. Translator remains one artifact and follows router core, never router-proxy.

### Masking

Mask splits into core, Jackson, and dynamic configuration artifacts:

- `team4u-mask`: policies, annotations, `FastMasker`, and no Jackson, Spring, Config, or proxy dependency.
- `team4u-mask-jackson`: existing Jackson serializer FQCNs.
- `team4u-mask-config`: Config-driven rules, repository, JSON rule decoding, and lifecycle bootstrap.

Unknown, null, blank, or empty mask policy names fail closed. Only an explicit `NONE` policy may return the original value.

### Bean

`team4u-bean` becomes Spring-free core. `SpringBeanContainer` keeps its FQCN but moves to `team4u-bean-spring`, which exposes plain `Team4uBeanConfiguration`. Consumers import it explicitly with `@Import`; this matches config-spring and avoids Boot-style auto-configuration.

### Logging

Logging is the final functional split. `team4u-log-core` accepts explicitly injected serializers and interceptors, defaults to plain text rather than Jackson, and excludes Spring, Config, Mask, Proxy, Criterion, and ByteBuddy. `team4u-log-governance` owns configuration reload, proxy integration, Jackson serialization, masking, and Spring integration.

### Evidence And Release

Advertised Criterion, Router, KV L1, and Proxy paths receive JMH benchmarks. Performance copy may claim zero allocation only when the GC profiler reports `gc.alloc.rate.norm = 0 B/op`, and may claim nanosecond latency only with a measured median and environment caveat. Final release gates run the full reactor, consumer invoker tests, release packaging, dependency assertions, and JDK matrix.

The graph is acyclic. Adapter and provider choices are visible in Maven dependency management and consumer runtime classpaths.

## Delivery Model

The approved implementation plan contains eighteen independently reviewed tasks. Every task is implemented by a fresh implementation subagent and reviewed by a separate review subagent. Each task keeps its own RED/GREEN evidence, module acceptance, full reactor gate, migration documentation, commit, and rollback procedure.
