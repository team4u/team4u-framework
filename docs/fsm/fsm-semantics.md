# 状态机语义手册

本文精确定义 `team4u-fsm` 的匹配、执行、异常与并发语义。这些行为全部有对应测试锚定，是组件的稳定契约。

---

## 1. 定义模型

- 状态机由 `StateMachine<S, E, C>` 表示：构建完成后迁移集合、状态集合、事件集合全部冻结，实例不可变。状态集合由初始状态、各规则的精确来源状态与固定目标状态按首次出现顺序组成（`stay()` 保持当前状态，不引入新状态）；仅在守卫或动作代码里引用、从未被定义声明的状态不属于状态集合，`getStates()` 与状态图均不包含它们。
- 一条迁移 `Transition<S, E, C>` 由以下要素构成：

| 要素 | 说明 |
| :--- | :--- |
| 来源 | 精确状态，或 `fromAny()` 任意来源 |
| 事件 | 精确事件，或 `onAny()` 任意事件 |
| 目标 | 构建期固定的精确状态，或 `stay()` 保持当前状态 |
| 守卫 | 0 个或多个，按声明顺序短路与 |
| 动作 | 0 个或多个，按声明顺序执行 |
| 标识 | `named(...)` 显式指定，否则按声明序号生成 `transition-N`（N 从 1 开始）；若该标识已被显式命名占用，追加确定性后缀 `-2`、`-3`… 直到空闲（如 `transition-2-2`），生成标识与显式标识永不冲突 |

- 守卫与动作通过 `TransitionContext<S, E, C>` 访问机器标识、迁移标识、来源状态、事件、目标状态与业务上下文。上下文不可变，`getTo()` 返回构建期决定的目标（`stay()` 迁移返回来源状态）。

## 2. 匹配顺序

迁移按“具体度”分三层，层间顺序固定，层内按声明顺序取**第一条守卫通过**的规则：

1. **精确层**：精确状态 + 精确事件；
2. **单边通配层**：两个桶按声明顺序归并成一条流——
   - 精确状态 + 任意事件（`from(A).onAny()`）；
   - 任意状态 + 精确事件（`fromAny().on(B)`）；
3. **全局兜底层**：任意状态 + 任意事件（`fromAny().onAny()`）。只有这一层是 any-any 全局兜底；`fromAny().on(B)` 属于单边通配桶，不是全局兜底。

关键保证：

- **精确规则（精确状态 + 精确事件）永不先输给通配规则**：即使全局规则声明在前，`from(A).on(B)` 也优先于 `fromAny().on(B)` 被评估。跨层遮蔽只发生在更具体的层未命中时，这是设计允许的部分遮蔽，构建期不会拒绝。
- **同层按声明顺序，带守卫候选先评估，无条件规则必须殿后**：同一匹配桶内，前置的无条件规则之后的任何规则都会被构建期拒绝（见第 3 节），因此同一桶内不存在“有意遮蔽”。真正允许有意遮蔽的位置只有一处：两个单边通配桶之间的重叠——例如 `from(A).onAny()` 无条件规则先声明、`fromAny().on(B)` 后声明时，状态 A 收到事件 B 会先命中前者，而后者在其他状态下仍可命中，因此合法。
- **评估即计费**：`TransitionResult.getEvaluatedTransitionCount()` 记录本次判定实际评估过的候选迁移数量，包括守卫未通过的规则与不带守卫的无条件规则（无条件规则被评估即命中），不是仅统计守卫执行次数。可用于监控匹配开销。

## 3. 构建期校验

`build()` 时拒绝以下定义，全部抛出 `StateMachineDefinitionException`：

| 校验 | 示例 |
| :--- | :--- |
| 标识为空或重复 | 两条规则同名 `"submit"` |
| 规则不完整 | 声明了 `on(...)` 却没有 `to(...)`/`stay()` 就 `build()` |
| 空定义 | 没有任何迁移 |
| 同桶兜底序错误 | 同一 `来源+事件` 桶内，无条件规则之后还有其他规则（后者永不可达） |
| 构建器复用 | 构建成功后对同一构建器再次 `build()` 或继续声明规则 |

另一部分校验在 DSL 声明期立即失败（不等 `build()`）：空机器标识、空状态/事件/目标、空守卫或空守卫描述、对同一条规则重复 `named(...)`、在 `to(...)`/`stay()` 之后追加守卫等，同样抛出 `StateMachineDefinitionException`。

注意“同桶不可达”校验按桶进行：`from(A).onAny()` 无条件规则先声明、`fromAny().on(B)` 后声明的跨桶部分遮蔽**不会**被拒绝——后者在其他状态下仍可命中，这是唯一允许“有意遮蔽”的位置（见第 2 节）。

**构建器生命周期**：只有成功返回状态机的 `build()` 才会关闭构建器。校验失败的 `build()` 不会关闭它——此前已声明的规则全部保留，未完成的规则阶段（已 `on(...)`/`onAny()` 但尚未 `to(...)`/`stay()`）也可以随后补全，修正后再次 `build()` 即可；调用方同样可以选择直接丢弃构建器重新开始。构建成功后，对构建器的任何后续操作（再次 `build()`、`from`/`fromAny`、`named`、`action` 等）都会抛出 `StateMachineDefinitionException`。

## 4. 触发语义

`fire` 与 `tryFire` 共享同一判定与执行流程，区别仅在拒绝时的表达方式：

| 情形 | `fire` | `tryFire` |
| :--- | :--- | :--- |
| 命中且守卫通过、动作成功 | 返回 `TransitionResult`（`TRANSITIONED`） | 同左 |
| 无任何候选迁移 | 抛 `TransitionRejectedException`（outcome=`NO_TRANSITION`） | 返回结果（`NO_TRANSITION`） |
| 有候选但守卫全部拒绝 | 抛 `TransitionRejectedException`（outcome=`GUARD_REJECTED`） | 返回结果（`GUARD_REJECTED`） |
| 守卫抛异常 | 抛 `TransitionExecutionException`（phase=`GUARD`） | 同左 |
| 动作抛异常 | 抛 `TransitionExecutionException`（phase=`ACTION`） | 同左 |

补充规则：

- **快速失败**：守卫或动作一旦抛出异常，引擎不会再尝试任何后续候选规则。异常语义是“本次触发失败”，不是“这条规则不适用”。
- **`NO_TRANSITION` 与 `GUARD_REJECTED` 的区分**：前者表示状态+事件组合无规则可走，后者表示有规则但条件不满足。两者的处置策略通常不同（前者可能是缺陷，后者是正常业务拒绝）。
- **`nextState(state, event, context)`**：`fire` 的便捷形式，仅返回目标状态。
- **`isTerminal(state)`**：判断状态是否没有任何可能出边（存在任意全局来源规则时所有状态都视为可迁移）。不执行守卫。

## 5. 动作失败与事务边界

- 动作按声明顺序执行，前一个动作抛异常则后续动作不再执行，本次迁移视为失败。
- **引擎不提供回滚，也不感知事务**。若动作包含写操作，调用方应自行决定事务边界：
  - 常见做法 A：在调用方的事务方法内先 `tryFire`/`fire`，动作只做纯内存修改或幂等记录，事务提交时一并生效；
  - 常见做法 B：把外部副作用（发消息、调接口）放到拿到 `TransitionResult` 之后执行，避免动作半途失败留下悬挂副作用。
- 引擎不发布任何事件。需要广播迁移结果时，由调用方消费 `TransitionResult`（含完整来源/目标/迁移标识）自行发布，或在外层编写适配器。

## 6. 线程安全职责划分

| 对象 | 线程安全 | 说明 |
| :--- | :--- | :--- |
| `StateMachine` / `Transition` / `TransitionResult` / `TransitionContext` | 安全 | 不可变，构建后冻结，可任意并发共享 |
| `StateMachineBuilder` | 不安全 | 仅启动期单线程使用；只有成功的 `build()` 会关闭它，失败的 `build()` 后仍可继续使用（见第 3 节） |
| 守卫 / 动作（调用方实现） | **由调用方负责** | 同一实例可能被多线程并发调用 |
| 业务上下文 `C` | 由调用方负责 | 引擎只透传引用，不加锁不复制 |

## 7. Mermaid 状态图

`StateMachineMermaid.render(machine)` 输出 `stateDiagram-v2` 文本：

- 每个状态以 `state "名称" as sN` 别名声明。渲染器对状态名、事件名与守卫描述做逐字符转义：回车符（`\r`）被剔除，换行符（`\n`）折叠为空格，双引号、分号与井号分别编码为 Mermaid 实体 `#quot;`、`#59;`、`#35;`，因此包含这些保留字符的 `toString()` 输出可以安全渲染——分号不会提前终结语句，井号也不会被误读为实体前缀；
- 图中状态集合即 `machine.getStates()`：只包含初始状态、精确来源状态与固定目标状态；仅在守卫或动作代码里引用的状态不会被渲染（见第 1 节）；
- 初始状态表示为 `[*] --> 初始状态`；
- 任意来源迁移渲染为合成节点 `*(any state)` 的出边；任意事件在边标签显示为 `*(any event)`；
- `stay()` 迁移渲染为自环；
- 守卫描述以 `[描述]` 追加在边标签之后；
- 输出顺序稳定：按状态首次出现顺序与迁移声明顺序，同一状态机渲染结果确定。

## 8. 核心刻意排除项

以下能力不在核心、也不计划进入核心，需要时在调用方或独立适配模块实现：

- 流程引擎式编排（Flow：节点、连线、并行网关）；
- Spring 集成、Bean 名称反射查找、注解扫描、全局单例注册表；
- 动态规则来源（JSON / 数据库 / 配置中心热更新）；
- 事件总线与领域事件发布；
- 状态持久化与事务管理。

理由：上述每一项都会把“不可变定义 + 无状态迁移引擎”拖回“运行期反射 + 全局状态”的旧路。核心保持零依赖后，这些能力都可以在调用方用几十行适配代码补上，且不污染引擎语义。
